# 环境与事件方案

状态：设计稿（已过一轮讨论）
影响：用户数据目录结构、主进程启动流程、MCP 合规性、新增事件通道
兼容性：磁盘结构与一个 MCP 端点不变，升级由迁移脚本负责

相关规范：[MCP 2026-07-28 Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)、
[Subscriptions](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/subscriptions)、
[Versioning](https://modelcontextprotocol.io/specification/versioning)

---

## 1. 要解决的四件事

1. **环境不是一个目录。** 现在隔离靠 `session.fromPartition('persist:<env>')`，落盘在 `Partitions\<env>`，只是 Chromium 的存储分区；用户数据（历史、书签、密码、权限）却放在全局 JSON 里靠 `envId` 字段打标签。结果是"一个环境"横跨两类位置，拷走、备份、删除都对不干净。实测这台机器 `Partitions\` 下有 36 个目录，`envs.json` 只登记 14 套环境——22 个孤儿，全是因为删环境时 `rm` 失败被 `catch` 吞掉（[tool-catalog.ts:670](../src/main/services/tool-catalog.ts#L670)）。
2. **浏览器里发生的事只能靠轮询。** Agent 想等一个请求完成、想知道页面报了什么错，只能反复调 `net_list` / `page_console`。没有被动通道。
3. **MCP 实现不符合当前规范。** 详见第 3 节。最直接的一条：标准 MCP 客户端连上来会把 `GET /mcp` 的 JSON 响应当成 SSE 流解析，然后反复重连。
4. **每套环境的网络出口和 UA 完全一样。** 多账号场景下，环境隔离只解决"串号"，不解决"被认出是同一台机器"。

目标：**环境 = 一个目录**、**事件可以被动接收**、**MCP 合规**、**网络配置按环境**。

## 2. 决策摘要

| 项 | 决定 |
| --- | --- |
| 进程模型 | 单进程。**明确不启用多进程**，不做 `--instance`、实例注册表、每实例端口和 token |
| 环境单元 | 一个 Chromium profile 目录 + 一扇窗口 |
| 会话来源 | `session.fromPath(<root>/profiles/<envId>)` |
| 历史/书签/密码/权限 | 搬进对应 profile 目录 |
| 端口 | **一个端口、一个 token、一个 `mcp.json`**，多个面按路径复用 |
| Agent 面 | `POST /mcp`，MCP 严格合规，里面不放任何私有端点 |
| 程序面 | `/api/*`：`POST /api/call`、`GET /api/tools`、`POST /api/events`（`/api/batch` 后置） |
| SDK / CLI 走哪 | **`/api/*`（朴素 JSON），不碰 `/mcp`**；没有 `api` 字段的旧版 App 直接报错，不回退 |
| 事件传输 | **长轮询**（`POST /api/events`），不用 SSE |
| 事件位置标识 | **纯递增整数 `seq`**，起点是启动时的 `Date.now()` |
| 事件与 MCP 的关系 | 两条通道并行，在数据层汇合；事件不走 MCP 通知 |
| Agent 侧事件 | 阻塞式工具 `events_wait`，不是推送 |
| MCP 目标版本 | 同时兼容 2026-07-28 与 2025 握手时代（见 3.3） |
| 网络配置 | 每环境一份 `network.json`，代理先行 |
| 指纹引擎 | 暂不做，只预留字段；Canvas/WebGL/字体不在本期 |
| 保留不动 | 单实例锁、一个 MCP 端点、一个 token、`tabId` 全局唯一、`tab_list` 全局视图 |

单进程意味着 `tab_list` 仍然是一次内存遍历就能拿到所有环境的标签，`resolveTab` 仍然能按 `tabId` 全局定位，工具参数语义一个字都不用改。

代价：主进程崩溃时所有环境一起挂（渲染进程崩溃只挂那个标签页）；同一时刻全机只有一份 BrowserPilot。

## 3. MCP 协议现状与合规差距

### 3.1 当前规范已经变了

现在的 current 版本是 **2026-07-28**，不是 2025-06-18。这一版对 Streamable HTTP 做了破坏性修改，规范原文：

> Revision 2026-07-28 changed the behavior of Streamable HTTP... Changes included:
> - **Removal of the GET stream endpoint.**
> - **Removal of protocol-level sessions.**

也就是说，2025 时代那套「GET 开 SSE 流、`Mcp-Session-Id` 管会话、`Last-Event-ID` 续传」**全部没有了**。服务端到客户端的推送改成了 [`subscriptions/listen`](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/subscriptions)：一次 POST，响应体是一条长期不关的 SSE 流。

但 `subscriptions/listen` 的订阅词表是**封闭的**，只有四类 MCP 级变更：

| 字段 | 通知 |
| --- | --- |
| `toolsListChanged` | `notifications/tools/list_changed` |
| `promptsListChanged` | `notifications/prompts/list_changed` |
| `resourcesListChanged` | `notifications/resources/list_changed` |
| `resourceSubscriptions` | 指定 URI 的 `notifications/resources/updated` |

规范明确要求：**服务端 MUST NOT 发送客户端没有显式请求的通知类型**。浏览器事件（console、network、navigation）不在这套词表里，要挂上去必须定义扩展（走 SEP 流程）。另外 2026 版明确写了 **"Resumable SSE streams via `Last-Event-ID` are not supported."**，而我们需要续传语义。

**结论：事件通道保持独立。** 形状可以借鉴 `subscriptions/listen`（一次请求开流 → 先发 ack → 持续推 → 结束发一个 complete），但协议不复用。

### 3.2 我们现在的实现与规范的差距

| 项 | 规范要求 | 现状 | 严重度 |
| --- | --- | --- | --- |
| `GET /mcp` | 2025 版：SSE 或 **405**；2026 版：**405** | 返回 200 + JSON `{ok,tools}` | **高** |
| `Origin` 校验 | **MUST** 校验，无效返回 **403** | 没有 | **高**（DNS rebinding） |
| `MCP-Protocol-Version` / `Mcp-Method` / `Mcp-Name` 头 | 2026 版 **MUST** 带，不匹配返回 400 + `-32020 HeaderMismatch` | 完全不校验 | 中 |
| 未知方法 | 404 + `-32601` | 200 + JSON-RPC error | 中 |
| 会话 | 2026 版：忽略 `Mcp-Session-Id`，不得签发 | 不签发 | ✅ 本来就对 |
| 绑定 127.0.0.1 / Bearer 鉴权 | SHOULD / SHOULD | 都有 | ✅ |

第一条的危害是具体的：官方 SDK 的客户端连接时第一件事就是 `GET` 开 SSE 流，代码里 `response.ok` 为真就往 `_handleSseStream` 里送。我们把 JSON 当流喂给它，它解析不出任何 `data:` 行，然后按退避策略重连，无限循环。**表现是"连上了但一直重连"**，不是明确报错。

**修法与版本无关**：2026 版对旧版客户端的兼容指引是"GET 到 MCP 端点一律回 405"，2025 版规范说"不提供 SSE 就回 405"。所以 `GET /mcp → 405` 对所有版本都正确。

### 3.3 目标版本：按"世代"而不是版本号处理

社区现在把协议分成两个 **era（世代）**，不是一个版本号：

| era | 版本范围 | 连接方式 |
| --- | --- | --- |
| `legacy` | 2024-10-07 … 2025-11-25 | `initialize` 握手 |
| `modern` | 2026-07-28 起 | 无握手；`server/discover` 探测 + 每请求 `_meta` |

**判定要看版本值，不能只看有没有 `MCP-Protocol-Version` 头**——2025-06-18 之后的老客户端也会带这个头。

| 请求特征 | 按哪个世代处理 |
| --- | --- |
| body 是 `initialize`，或 `_meta` 里没有版本 | `legacy` |
| `_meta.io.modelcontextprotocol/protocolVersion` = `2026-07-28` | `modern` |
| 其他版本值 | 400 + `UnsupportedProtocolVersionError`，列出支持的版本 |

**现状与选择**（2026-11 调研）：

- 我们依赖的是 `@modelcontextprotocol/sdk@^1.30.1`（v1 线，**legacy 世代**）
- 官方 v2 拆成了 `@modelcontextprotocol/server@2.x`，最新 **2.4.0（2026-10-23）**，实现 2026-07-28，要求 Node ≥ 20。它的 `createMcpHandler(factory)` **默认同时服务两代**（`legacy: 'stateless'`），正好对上我们现在的无状态设计
- **主流 Agent 仍然走 legacy**：v2 客户端 SDK 的默认 `versionNegotiation.mode` 就是 `legacy`（`initialize` 握手），只有显式设 `auto` 才会用 `server/discover` 探测 modern

所以建议分两步：

1. **P0 先在 v1 上把 legacy 做对**（`GET /mcp → 405` + `Origin` + 路由拆分）。覆盖今天绝大多数 Agent
2. **要支持 modern 时，升级到 `@modelcontextprotocol/server@2.x` 的 `createMcpHandler`**，不要自己手写双世代分支。这一步需要一个独立的升级评估（API 有变化：`McpServer`、handler 注册方式、Node 版本要求）

### 3.4 合规修复清单

| # | 改动 | 位置 |
| --- | --- | --- |
| 1 | `GET /mcp` → 405（保留 Bearer 校验，先 401 后 405），同时删掉现在那个 `{ok,tools}` 响应 | [McpService.ts:120](../src/main/services/McpService.ts#L120) |
| 2 | `Origin` 校验：存在且不在白名单 → 403（对所有路径生效） | McpService 入口 |
| 3 | 2026 头校验：`MCP-Protocol-Version` / `Mcp-Method` / `Mcp-Name` 与体一致性，不匹配 400 + `-32020` | McpService 入口 |
| 4 | 未知方法 → 404 + `-32601` | McpService 分发处 |
| 5 | 路由表：`/mcp` 与 `/api/*` 分路径分发 | McpService 入口 |

1、2、5 是独立的小改动，可以先做；3、4 等目标版本确认后跟进。

原先"给 CLI 留一个 `GET /mcp`"的打算作废——CLI 改走 `GET /api/tools`。

### 3.5 三个面与路由

**一个端口、一个 token、一个 `mcp.json`，按路径复用。**

```
POST /mcp           Agent 面：MCP，严格合规，只做动作
POST /api/call      程序面：单个动作
POST /api/batch     程序面：多个动作（后置，见 3.6.2）
GET  /api/tools     程序面：全量工具目录
POST /api/events    程序面：长轮询事件（见第 6 节）
```

| 使用方 | 动作 | 工具目录 | 事件 |
| --- | --- | --- | --- |
| Agent（MCP 客户端） | `POST /mcp` | `tools/list` | `events_wait` 工具 |
| CLI（`browserpilot`） | `POST /api/call` | `GET /api/tools` | `POST /api/events` |
| 三个 SDK | `POST /api/call` | `GET /api/tools` | `POST /api/events` |

三条纪律：

1. **`/mcp` 里不放任何私有端点。** `/api/*` 是兄弟路径，不是 MCP 的子功能。这样 MCP 那条路可以做到严格合规，不用为了塞私货而迁就。
2. **鉴权、`Origin` 校验对所有路径一视同仁。** 同一个 token、同一套 403 规则，不出现"`/mcp` 严、`/api` 松"的口子。
3. **每个 handler 是独立函数，路由只做一张表。** 将来真要拆端口，就是把这张表挂到第二个 `createServer` 上，不重写。

### 3.6 程序面 `/api` 规格

程序面用**朴素 JSON**，不用 JSON-RPC。不用 JSON-RPC 的理由：不需要 id 管理，错误用 HTTP 状态 + `ok` 区分，批量是数组而不是协议特性。

#### 3.6.1 `POST /api/call`

```jsonc
// 请求
{ "tool": "page_click", "args": { "tabId": "tab-1a2b", "selector": "#go" } }

// 200
{ "ok": true, "control": "agent", "tabId": "tab-1a2b", "seq": 123,
  "image": { "mimeType": "image/jpeg", "data": "<base64>" } }
```

返回值就是工具载荷本身（和 `callTool` 的结果一致），图片作为同级字段，不再包成 content part。

#### 3.6.2 `POST /api/batch`（后置）

```jsonc
{ "calls": [ { "tool": "page_click", "args": {...} }, { "tool": "page_type", "args": {...} } ] }
→ { "results": [ { "ok": true, ... }, { "ok": false, "error": "..." } ] }
```

**顺序执行，不是事务**：中间某条失败，前面的已经生效了。它的价值只在于省往返（现在 `fill` 要三次往返）。

后置的理由：先把 `call` / `tools` / `events` 做扎实。另外注意——MCP 侧的 JSON-RPC 批量虽然规范在 2025-06-18 删掉了，但 SDK 1.31.0 还保留（`MAX_BATCH_SIZE = 100`，`server/requestBody.js`），所以 `/mcp` 上今天也能批量；**但那是 SDK 的向后兼容行为，不是规范保证**，我们不依赖它。

#### 3.6.3 `GET /api/tools`

```jsonc
{ "version": "0.19.0", "tools": [ { "name", "description", "inputSchema", "group" } ] }
```

返回全部 99 个，不受 `toolMode` 影响（`tools/list` 在 `toolMode: search` 下只有 13 个核心工具）。

#### 3.6.4 `POST /api/events`

见第 6 节。

### 3.7 错误规则（一条）

**解析成功且鉴权通过之后，永远返回 200，成败看 `ok`。**

| 情况 | 状态码 | 体 |
| --- | --- | --- |
| 工具执行失败 | 200 | `{"ok":false,"error":"..."}` |
| 工具名不存在 | 200 | 同上（与现有工具语义一致） |
| JSON 格式错、`args` 不是对象 | 400 | `{"ok":false,"error":"...","code":"bad_request"}` |
| 没带 token / token 错 | 401 | 空 |
| `Origin` 非法 | 403 | 空 |

这样 SDK 里只有一条错误分支：看 `ok`。HTTP 状态只用来区分"请求根本没进业务"。

### 3.8 发现与兼容

`mcp.json` 增加一个字段，仍然只有一个文件、一个 token：

```json
{
  "url": "http://127.0.0.1:39221/mcp",
  "api": "http://127.0.0.1:39221/api",
  "token": "..."
}
```

老的读者（`SKILL.md`、现有接入提示词）只读 `url`，不受影响；CLI 和三个 SDK 读 `api`。

**旧版 App 没有 `api` 字段时直接报错，不回退到 `/mcp`。**

理由：SDK 与 App 同号发布，跨版本混用不是支持场景；而回退会让行为悄悄降级（没有 `/api/batch`、错误语义不同、事件通道缺失），比报错难查得多。报错文案要给出出路：

> 本机装的 BrowserPilot 太旧，没有 `/api`。请升级，或用 `BROWSERPILOT_EXE` 指定新版本。

CI 里要钉版本就用 `BROWSERPILOT_EXE` 和 `BROWSERPILOT_STRICT_VERSION`。

## 4. 目录布局

```
%APPDATA%\BrowserPilot\                     ← Electron userData，不变
├─ envs.json                                环境清单
├─ groups.json                              标签分组
├─ settings.json                            应用设置
├─ workflows\                               工作流库，一文件一份（见 docs/存储方案.md）
├─ runs.db / recordings.json                运行记录（SQLite）、录屏索引
├─ cache-cleanup.json                       清理时间戳
├─ mcp.json                                 端点与 token
├─ profiles\
│   ├─ env-default\                         ← 一个完整的 Chromium profile
│   │   ├─ Network\Cookies                  Chromium 自己的
│   │   ├─ Local Storage\
│   │   ├─ Cache\
│   │   ├─ Service Worker\
│   │   └─ browserpilot\                    ← 应用自己的，子目录避免撞名
│   │       ├─ history.db                   SQLite（见 docs/存储方案.md）
│   │       ├─ bookmarks.json
│   │       ├─ passwords.json
│   │       ├─ permissions.json
│   │       └─ network.json                 代理、UA、语言、时区
│   └─ env-4a11c9fabc3f\
└─ Partitions\                              ← 迁移后删除
```

**profile 根目录直接就是 Chromium 的布局**，不会再套一层 `Default\`。应用自己的 JSON 放在 `browserpilot\` 子目录里，Chromium 不认识这个名字就不会碰。

### 4.1 什么留全局，什么进环境

| 文件 | 位置 | 理由 |
| --- | --- | --- |
| `envs.json` | 全局 | 环境清单本身，不能跟着环境走 |
| `settings.json` | 全局 | 应用级设置 |
| `workflows\` | 全局 | 工作流是可复用资产，同一份要在多套环境里跑；一文件一份，见 [`存储方案.md`](存储方案.md) |
| `runs.db` / `recordings.json` | 全局 | 跨环境查看运行记录、录屏索引 |
| `mcp.json` | 全局 | 只有一个端点 |
| `history.db` | `profiles\<env>\browserpilot\` | 用户数据，跟环境；SQLite，见 [`存储方案.md`](存储方案.md) |
| `bookmarks.json` | 同上 | 同上 |
| `passwords.json` | 同上 | 同上 |
| `permissions.json` | 同上 | 站点授权是环境级的 |
| `session.json` | 同上 | 现在是 `Record<envId, SessionState>`，拆分后每环境只留自己那份 |
| `network.json` | 同上 | 新增 |

搬完之后 **"拷走一个目录 = 搬走整套账号"** 成立，删环境就是删一个目录。

## 5. 迁移

### 5.1 前置条件

- **只在启动时、任何窗口打开之前执行**。Windows 上 Chromium 会占用 `Cookies` 等文件，运行中搬不动。
- 读 `migration.json`，已完成则整段跳过（幂等）。
- 迁移期间不启动 MCP，避免外部调用改数据。

### 5.2 步骤

1. **备份**（仅首次）：整个 root 复制到 `BrowserPilot.bak-<时间戳>`。空间不够就中止并提示，不允许无备份迁移。
2. **建目录**：`profiles\<env>\`。
3. **搬存储**：`Partitions\<env>` → `profiles\<env>`。同一卷内直接 `rename`（快、原子）；跨卷失败则退回复制 + 删除源。搬完检查 `profiles\<env>\Network\Cookies` 是否存在——**这是登录态是否搬过来的唯一硬证据**。
4. **拆全局 JSON**：`history.json` / `bookmarks.json` / `passwords.json` / `permissions.json` 按 `envId` 分组，写进对应 `profiles\<env>\browserpilot\`。`session.json` 是 `Record<envId, SessionState>`，按键拆。
   - 如果 [`存储方案.md`](存储方案.md) 的 S2（history → SQLite）已经先做完，这一步直接把 history 写进 `history.db`，省掉一次中间态迁移。
5. **校验**（见 5.3）。
6. **写标记**：`migration.json` 记录 `{ done, at, from, to, envs: [...], progress: [...] }`。
7. **收尾**：删除空的 `Partitions\`；孤儿目录（`envs.json` 里没有的）记进 `migration.json.orphans`，**不自动删**——那里面可能有用户忘记的账号。

### 5.3 校验项

| 检查 | 通过标准 |
| --- | --- |
| cookie 数据库 | 每套环境 `profiles\<env>\Network\Cookies` 存在（迁移前有的话） |
| 数据条数 | history / bookmarks / passwords / permissions 迁移前后总数一致 |
| 环境完整性 | `envs.json` 里每套环境都有对应目录 |
| 人工确认 | 抽一套环境打开一个需要登录的站点，确认是登录态 |

任何一项不过 → 中止并回滚。

### 5.4 dry-run

```
browserpilot migrate --dry-run
```

输出每套环境的：目录大小、`Cookies` 是否存在、各类 JSON 的条数、将要丢什么、预计耗时。默认不执行，必须显式 `--apply`。

### 5.5 回滚

- 迁移前有完整备份：把 `BrowserPilot` 改名，备份目录改回来即可。
- 迁移中途失败：`profiles\` 可能只搬了一部分，但 `Partitions\` 里已搬走的部分被 rename 掉了——所以每搬成功一套就在 `migration.json.progress` 里记一条，回滚时按记录把目录 rename 回去，再删 `profiles\`。

### 5.6 风险

| 风险 | 处理 |
| --- | --- |
| Windows 文件占用导致搬不动 | 只在启动早期执行，此时没有任何 WebContents |
| 跨卷 rename 失败 | 回退到复制 + 校验 + 删源 |
| 迁移中途崩溃 | 逐环境记录进度，重跑从断点继续 |
| 密码跨机不可用 | `safeStorage` 密钥绑定 OS 登录用户，目录拷到别的机器 cookie 能用、密码解不开 |
| 备份占空间 | 迁移完成后提示用户确认再删备份 |

## 6. 事件协议（长轮询 + seq）

### 6.1 为什么不用 SSE

| 维度 | SSE | 长轮询 |
| --- | --- | --- |
| 首个事件延迟 | 即时 | **一样即时**（有事件时立刻返回挂起的请求） |
| 空闲开销 | 零 | **一样零** |
| 三个语言解析 | 各写一个 SSE 行解析器 | `json.loads` / `JSON.parse` / `json.Decode` |
| 重连状态机 | 需要 | **不需要**，每次独立请求 |
| 每订阅者队列 / 丢弃策略 | 需要 | **不需要**，返回多少由服务端定 |
| 背压 | 要查 `writableLength`、发 `dropped` | **天然有** |
| 取消 | 关流，服务端处理 close | 客户端放弃请求 |
| 测试 | 要真读流 | `curl` 一个 POST |

真正丢掉的只有"同一批里连续事件逐条推送"，在 localhost 上是 1–3ms 的差别，而且我们会按批量上限合并，可以忽略。

另外：2026 版 MCP 已移除 GET 流，新增一条 GET SSE 端点与"所有请求都是 POST"的方向相反；长轮询 `POST /api/events` 更一致。

**事件缓冲与 `seq` 是传输无关的**，将来真需要 SSE，在同一个缓冲上再加一个 40 行的 GET 端点即可，不动核心。

### 6.2 seq 的定义

`seq` 是进程内单调递增整数，**起点是启动时刻的 `Date.now()`**，每个事件加一。

起点不能用 0 或 1：App 重启后计数归零，客户端拿着旧的 `1042` 重连，如果新进程已经产生到 2000 条，服务端会以为"你要 1043 之后的"并正常返回——**客户端拿到的是另一批事件，还以为自己没漏**。这是静默错误，比报错糟糕。

起点用时间戳之后，旧客户端的 `seq` 永远小于新起点，服务端一眼判定"太旧"。

`epoch`（启动随机串）保留，但**降级为信息字段**，只用于诊断和判断"App 是否重启过"，不参与定位。

### 6.3 请求

```
POST /api/events
Authorization: Bearer <token>
Content-Type: application/json

{
  "since": 1758765432150,        // 上次响应里的 seq；不传 = 只订阅新事件
  "wait": 25000,                  // 最长挂多久（毫秒），0 = 不挂起；上限 25000
  "limit": 200,                   // 一次最多返回多少条，上限 200 条 / 256KB
  "types": ["page.console", "net.*"],
  "env": "env-default",
  "tabId": null
}
```

命名约定：**入参叫 `since`（我拿到这儿了），出参叫 `seq`（你现在到这儿了）**。和 `events_wait` 的参数一致，SDK 里就是 `since = 上次响应的 seq`。

用 POST 而不是 GET：过滤器是结构化的，避免 URL 编码和长度限制，也与"动作都走 POST"一致。调试用：

```bash
curl -s -X POST http://127.0.0.1:39221/api/events \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"wait":5000}'
```

### 6.4 响应

```jsonc
// 1. 有事件（可能一次多条，突发被天然合并）
{
  "epoch": "7f3a1c",
  "seq": 1758765432173,          // 这批最后一条的 seq，客户端存下来下次传回
  "events": [ ... ],
  "more": false                   // true = 缓冲里还有，立刻再请求
}

// 2. 挂到超时也没事件
{ "epoch": "7f3a1c", "seq": 1758765432150, "events": [], "timeout": true }

// 3. 位置失效，必须用工具重建状态
{ "epoch": "9ab2d1", "reset": true, "seq": 1758800000001, "events": [ ... ] }

// 4. 中间漏了（缓冲溢出）
{ "epoch": "7f3a1c", "seq": 1758765432999, "events": [ ... ], "gap": 340 }
```

### 6.5 位置判定（服务端三档）

设缓冲区间 `[start, next)`，请求里的 `S`：

| 情况 | 判定 | 返回 |
| --- | --- | --- |
| 未传 `S` | 只订阅新事件 | 不回放，从现在开始 |
| `S < start` | 太旧，超出缓冲（含"上次启动的 seq"） | `reset: true` + 当前 seq |
| `start <= S < next` | 正常 | 从 `S+1` 开始发，最多 `limit` 条 |
| `S >= next` | 在未来（重启过或篡改） | `reset: true` |

### 6.6 缓冲与背压

- 环形缓冲：最近 **2000 条或 5 分钟**，先到者为准
- **没有每订阅者队列**：慢客户端只会拿得少、拿得晚，不会拖慢页面
- 缓冲溢出导致的缺口，在客户端下次请求时以 `gap` 字段告知，**绝不静默丢**
- 同时挂起的请求数封顶 **8 个**；超出立刻返回空响应，让客户端下一轮再来（防止异常客户端吃光 fd）

### 6.7 事件清单

触发点都是现成的 Electron 事件，不需要新机制。

| type | 触发点 | payload |
| --- | --- | --- |
| `env.window` | 环境窗口打开 / 关闭 / 切换有头无头 | `state`, `headless` |
| `tab.created` / `tab.closed` | 标签增删 | `url`, `title` |
| `tab.navigation` | `did-start-navigation` / `did-navigate` / `did-stop-loading` / `did-fail-load` | `phase`, `url`, `error?` |
| `tab.title` | `page-title-updated` | `title` |
| `tab.favicon` | `page-favicon-updated` | `icons` |
| `tab.media` | `media-started-playing` / `media-paused` | `state` |
| `page.console` | `console-message`（[console-log.ts:47](../src/main/console-log.ts#L47) 已在收） | `level`, `message`, `line`, `source` |
| `page.dialog` | alert / confirm / prompt / beforeunload | `type`, `message` |
| `page.unload-blocked` | `will-prevent-unload` | `url` |
| `download` | `will-download` + DownloadService 进度 | `phase`, `id`, `name`, `bytes`, `total` |
| `net.request` / `net.response` / `net.failed` | CDP `Network.*` | `reqId`, `method`, `url`, `status?`, `resourceType`, `bytes?` |
| `control.changed` | 接管 / 交还 / 共享 | `control`, `reason` |

**`net.*` 只在抓包开着时产出**（跟随 `net_start` / `net_stop`，不另造开关）。没在抓包的页面不该往缓冲里灌数据。

`workflow.*`（运行开始、节点完成、失败）留到后续，需要 RecordService 埋点。

### 6.8 高频合并

| 事件 | 策略 |
| --- | --- |
| `net.*` | 只在抓包开着时产出 |
| `download.progress` | 同一 id 每 500ms 最多一条，只留最新 |
| `page.console` | 同一 tab 连续相同消息 1s 内折叠，带 `repeated: n` |
| 其余 | 不合并 |

### 6.9 边界

- **这条通道只观察，不能执行动作**。所有动作仍然只有工具。`docs/技术方案.md` 里「不另开私有通道」的原则依然成立，补的是"观察必须有一条路"
- 事件里不放 cookie 明文、不放请求体、不放截图
- 鉴权复用 MCP 的 token，不新增凭据
- `Origin` 校验与 MCP 端点一致

## 7. MCP 与事件通道怎么配合

MCP 通道**不能主动推**（2026 版连 GET 流都删了），所以两条通道并行，在**数据层**汇合：

```
                     ┌── 事件缓冲（一份，seq 单调递增）
采集管线 ── write ───┤
 CDP Network         ├── read：POST /api/events（长轮询）──→ SDK / 脚本
 console             ├── read：工具 events_wait ─────→ Agent（走 MCP）
 navigation          └── read：工具 net_list（快照）──→ Agent
 download
```

### 7.1 Agent 场景：启动抓包后怎么拿请求

模型在两次工具调用之间没有生命周期，不能异步接收推送。所以 Agent 侧的事件消费形态是**阻塞的工具调用**：

```
1. agent → tools/call net_start {tabId}
   ← {ok:true, capturing:true, seq:1758765432150}
2. （页面开始产生请求，采集进缓冲）
3. agent → tools/call page_click {tabId, selector:"#next"}
   ← {ok:true, seq:1758765432161}
4. agent → tools/call events_wait {tabId, types:["net.response"], since:1758765432161, timeout:30}
   ← {ok:true, events:[...], seq:1758765432173}
5. agent → tools/call net_stop
```

### 7.2 动作类工具必须返回 seq

如果 `net_start` / `page_click` 不返回 seq，"点击"和"开始等待"之间发生的事就漏掉了。所以：

- **所有工具结果里带 `seq`**（当前缓冲位置）
- `events_wait` 接受 `since`，从那个位置往后取

这样"我点了一下 → 我看看这一下触发了什么请求"就成立，不需要靠猜时间窗。

实现上就是在工具的 `finish()` 里加一行（[tool-catalog.ts:145](../src/main/services/tool-catalog.ts#L145)）。

### 7.3 events_wait 工具

```
events_wait {
  since?: number      // 从这条之后开始；不传 = 从现在开始
  types?: string[]    // 默认全部
  env?: string
  tabId?: string
  timeout?: number    // 秒，默认 30，上限 60
  limit?: number      // 默认 100，上限 200
}
→ { ok: true, events: [...], seq: number, timeout?: boolean }
```

超时上限 60 秒是刻意的：工具默认超时 90 秒（[tool-catalog.ts:335](../src/main/services/tool-catalog.ts#L335)），留 30 秒余量。

### 7.4 脚本场景

脚本自己既是动作发起者又是事件消费者，同一进程两路并发：

```python
page.click("#next")                                   # MCP 工具
for event in bp.events(types=["net.response"], since=seq):
    print(event["payload"]["url"])                    # 长轮询
```

### 7.5 net_list 与事件的关系

不是两套数据，是**同一份采集存储的两种读法**：

| 入口 | 形态 | 用途 |
| --- | --- | --- |
| `net_list` | 快照 | Agent 事后清点、脚本一次性读取 |
| `events_wait` / `/api/events` | 增量 | Agent 等下一个请求、脚本实时处理 |

**事件必须由写采集存储的同一处代码产生**，否则两边会慢慢不一致。这是实现时的硬约束。

### 7.6 超时预算

| 通道 | 上限 | 理由 |
| --- | --- | --- |
| `/api/events` 的 `wait` | 25s | 短于常见 30s 空闲超时，SDK 自己会重连 |
| `events_wait` 的 `timeout` | 60s | 工具默认超时 90s，留余量 |
| SDK 传输层超时 | `wait` + 10s | 避免客户端先超时 |

## 8. 每环境网络配置

`profiles\<env>\browserpilot\network.json`：

```json
{
  "proxy": { "mode": "direct" },
  "userAgent": null,
  "acceptLanguages": "zh-CN,zh;q=0.9",
  "timezone": null,
  "locale": null,
  "webrtcPolicy": "default",
  "fingerprint": {}
}
```

| 字段 | Electron 接口 | 应用时机 | 说明 |
| --- | --- | --- | --- |
| `proxy` | `session.setProxy()` | 会话创建后、首次导航前 | `mode`: `direct` / `fixed`（`rules` 用 Chromium 语法）/ `pac` |
| `userAgent` + `acceptLanguages` | `session.setUserAgent(ua, acceptLanguages)` | 同上 | 一个调用同时设两项，不用改请求头 |
| `timezone` | CDP `Emulation.setTimezoneOverride` | debugger attach 后，且每次主框架导航后重发 | 覆盖是 per-target 的，导航不会自动保留 |
| `locale` | CDP `Emulation.setLocaleOverride` | 同上 | |
| `webrtcPolicy` | `webContents.setWebRTCIPHandlingPolicy()` | 每个标签创建时 | **WebContents 级**，不是 Session 级，按标签逐个下发 |
| `fingerprint` | — | — | 本期留空对象，不动结构 |

### 8.1 顺序很重要

**没有独立代理，其他伪装意义很小。** 同一出口 IP 就能把几十个账号串起来看。落地顺序：

1. 代理（`setProxy`，成本最低、价值最高）
2. UA + 语言（一个 `setUserAgent` 调用）
3. 时区 / locale（CDP，要处理导航后重发）
4. 其余（本期不做）

### 8.2 指纹引擎为什么不做

Canvas / WebGL / Audio 噪声、字体枚举、硬件参数伪装，需要 `Page.addScriptToEvaluateOnNewDocument` 在页面脚本之前注入，并且要长期跟浏览器版本对抗。做浅了无效（一眼假），做深了是专业指纹浏览器数年的积累。

而且它和 `docs/技术方案.md` 末尾「不做指纹引擎」的决定直接冲突——那条要改，是产品定位层面的决定，不是技术选型。因此本期只预留 `fingerprint` 字段。

### P2 的语义细节

- `seq` 起点是启动时刻的 `Date.now()`，客户端拿到的旧值一定小于新起点，服务端据此判定 `reset`
- **动作类工具返回的 `seq` 是动作完成后的位置**。对 `page_click` 这类"点完才异步请求"的动作，配合 `events_wait {since}` 正好；但 `page_navigate` 会阻塞到 load 完成，导航事件在返回值之前就已发生——想让 Agent 看到这些事件，要在动作**之前**取 `seq`（任意一个工具结果里都有）
- `page.console` 对同一标签 1 秒内重复的同一条日志直接丢弃，避免死循环 `console.log` 刷爆缓冲

### P3 实测（本地 CONNECT 代理）

```
配置前 env-default 启动窗口的流量        => 代理日志文件不存在（直连）
network_set env-a fixed http://127.0.0.1:18080
```

校验（单元级，`setProxy` 打桩）：

```
接受  http://127.0.0.1:18080 / socks5://127.0.0.1:1080 / host:8080 / [::1]:7890 / user:pass@10.0.0.5:3128
拒绝  "不是代理!!"（主机名只允许 ASCII 字母数字点横线或 [IPv6]）
拒绝  pac 模式缺 pacScript、非法 webrtcPolicy
下发  fixed => setProxy({proxyRules, proxyBypassRules})；UA/语言 => setUserAgent(ua, langs)
失败  setProxy 抛错 => network_get.error 保留错误，不静默回退直连
```

### P3 实现说明

- 配置在**窗口创建时**下发，不是进程启动时：环境窗口可能一直不开，没必要提前建会话
- `addTab` 里首个 `loadURL` 包在 `networkReady(envId).then(...)` 里，保证**第一个请求就走代理**，否则首屏会直连出去
- P1 之后每套环境是独立 profile，所以代理天然按环境隔离；`env_delete` 会 `forgetNetwork` 清缓存
- **没做的**：`timezone` / `locale` 只存不生效（需要 CDP `Emulation.setTimezoneOverride` / `setLocaleOverride`，且每次主框架导航后要重发），`fingerprint` 仍是空对象

### P3

- [x] 两套环境配不同代理，出口不同（本地 CONNECT 代理实测：env-a 导航 example.com 出现 `CONNECT example.com:443`，env-default 同站点导航代理日志新增 0 行）
- [x] 配置写进 `network.json`，重启后仍生效（重启后 `network_get` 读回同一份配置，开窗口后 `applied=true`，代理日志继续增长）
- [x] 无效代理有明确报错，不静默回退直连（`规则看不懂` 校验；`setProxy` 失败时 `network_get.error` 留错误，不假装成功）

## 12. 明确不做

- 多进程；`--instance`；实例注册表；每实例端口和 token
- 事件走 MCP 通知（`subscriptions/listen` 词表封闭，且没有续传）
- SSE 端点（缓冲与 seq 传输无关，将来需要再加）
- 第二个端口、第二个 token（`/api/*` 与 `/mcp` 同端口同 token）
- SDK 回退到 `/mcp`（旧版 App 直接报错）
- 指纹引擎（Canvas / WebGL / Audio / 字体 / 硬件参数）
- 网卡级抓包
- 跨环境的全局历史查询（历史跟着环境走）
- 通过事件通道执行任何动作

## 13. 实测结论（已完成）

两条技术未知数都已实测通过。环境：Windows 11 + Electron 45.2.3。
本机必须加 `--no-sandbox`（Chromium 沙箱在这个会话里起不来，正常启动返回 `0x80000003` STATUS_BREAKPOINT）——这是环境限制，不是产品问题；正常桌面不需要这个开关。

### 13.1 单实例锁按 userData 目录隔离 —— 通过

```
pid=61304 userData=...\.probe-a lock=true
pid=10552 userData=...\.probe-a lock=false     ← 同一目录，第二个进程拿不到锁
pid=11496 userData=...\.probe-b lock=true      ← 不同目录，两个进程能并存
```

说明 `requestSingleInstanceLock()` 确实按 userData 目录加锁。虽然本期不做多进程，这条确认了"改成每环境一个 userData 就天然并行"的推理成立。

### 13.2 `Partitions\<env>` 搬到 `profiles\<env>` 后 cookie 完好 —— 通过

```
partition-set       all=[probe=from-partition]
frompath-before     all=[probe=from-partition]                        ← 目录搬迁后读到了
frompath-after-write all=[probe=from-partition,second=from-path]
frompath-before     all=[probe=from-partition,second=from-path]       ← 重启后都还在
```

两条结论：

1. **迁移可以整目录搬**：`Move-Item Partitions\probe-env profiles\probe-env` 之后，`session.fromPath` 能读到原来的 cookie。不需要解析 Chromium 的库文件
2. **`session.fromPath` 是真持久化**：新写的 cookie 重启后仍在

### 13.3 踩到的一个坑：会话 cookie 不落盘

第一次跑出来的结果是"持久化失效"，实际原因是测试里 `cookies.set` 没给 `expirationDate`——那是会话 cookie，Chromium 本来就不写盘。**迁移校验必须用带过期时间的 cookie**，否则会把迁移误判成失败。

### 13.4 复跑命令

```powershell

$exe = "$PWD\node_modules\electron\dist\electron.exe"

# 1. 单实例锁

```
