状态：设计稿（已过一轮讨论）
影响：用户数据的落盘格式、工作流的安装与去重、历史与运行记录的写入方式
依赖：`docs/环境与事件方案.md` 的 P1（目录迁移）会改变 history 的归属位置

## 2. 四个问题

### 2.1 写不是原子的

```ts
// StorageService.ts:71
function writeJson(name: string, value: unknown): void {
  mkdirSync(app.getPath('userData'), { recursive: true })
  writeFileSync(file(name), JSON.stringify(value, null, 2), 'utf8')
}
```

`writeFileSync` 先截断再写。崩在半路，文件就是半截 JSON。

### 2.2 读失败静默清空

```ts
// StorageService.ts:61
function readJson<T>(name: string, fallback: T): T {
  try {
    return JSON.parse(readFileSync(path, 'utf8')) as T
  } catch {
    return fallback          // 没有日志、没有备份、没有隔离
  }
}
```

2.1 和 2.2 合起来是个数据丢失闭环：**写到一半崩 → 下次启动解析失败 → 返回 `[]` → 下次写入把 `[]` 写回 → 数据真的没了**，而且用户和开发者都不知道发生过什么。

### 2.3 每次改动重写整份

`history.json` 394 KB，而 `page-title-updated` / `did-finish-load` 都会触发 `rememberHistory`（`windows.ts:1203` 起），每次都整份重写。导航几百次就是几十 MB 的写入量。

### 2.4 工作流只有一份合并文件

见第 5 节。

## 3. 原则：按访问模式分，而不是"统一换掉"

这不是我们发明的分法，**Chrome 自己就是混着用的**：

| Chrome profile 里的文件 | 格式 |
| --- | --- |
| `Bookmarks` | JSON |
| `Preferences` | JSON |
| `History` | **SQLite** |
| `Login Data` | **SQLite** |

规律：

- **小配置、文档型**（整存整取、人可能手改）→ JSON 文件
- **记录型**（只增、要按时间/字段查、会长大）→ SQLite
- **对外合同**（别的进程要读）→ JSON，且格式不能随便动

## 4. 决策表

| 文件 | 决定 | 理由 |
| --- | --- | --- |
| `history` | **SQLite**，每环境一个 | 394 KB 且高频写，要按时间/域名查 |
| `runs` | **SQLite**，全局一个 | 只增、要按时间保留、要按工作流查 |
| `workflows` | **一文件一份**（第 5 节） | 文档型，整存整取，要能直接拷贝/分享 |
| `recordings` | 暂留 JSON | 20 KB，低频；涨起来再迁 |
| `envs` / `groups` | 留 JSON | 小，且启动早期就要读 |
| `settings` | 留 JSON | 小，可能被手改 |
| `bookmarks` / `passwords` / `session` / `permissions` | 留 JSON | 全部 < 4 KB |
| `mcp.json` | **必须留 JSON** | SDK 和 Agent 读的对外合同，换了等于自断接口 |
| `cache-cleanup` | 留 JSON | 一个时间戳 |

`node:sqlite` 是 Node 内置的，**Electron 里直接可用**，不需要装 native 模块（也就不受 `npmRebuild: false` 影响）：

```
node     v24.15.0 → DatabaseSync, StatementSync, Session, backup
electron 24.22.2 → 同上
```

代价是 `DatabaseSync` 是同步 API，会阻塞主线程——几百行的查询没问题，但不能在大表上做无索引的全表扫。

## 5. 工作流：一文件一份

### 5.1 现在的问题

安装链路（`MarketService.installMarketFile`）：

```
拉 GitHub 原始 JSON → importWorkflowText 校验 → workflowWrite 按 app.name 去重 → 整份重写 workflows.json
```

三个毛病：

1. **原始 JSON 不留副本。** 只保留归一化后的结构，还顺手把 `conversation_variables` 清空（`RecordService.ts:172`）。市场里工作流升级了无法 diff、无法回滚；导出是从内部结构反序列化，未必等于原文件。
2. **去重键是 `app.name`**（`RecordService.ts:89`）。市场里两个不同 slug 同名的会互相覆盖；本地改个名再装就变成两份。
3. **整份重写 + 非原子**：一次损坏，所有工作流一起没。

### 5.2 目标布局

```
%APPDATA%\BrowserPilot\
└─ workflows\
    ├─ boss-auto-apply.json      ← 市场原始 JSON，原样保存
    ├─ bilibili-download.json
    └─ wf-3f9a2c.json            ← 自己录的
```

工作流是**跨环境复用**的资产，所以放全局，不进 `profiles\`（与 `docs/环境与事件方案.md` §4.1 一致）。

| 操作 | 现在 | 改成文件后 |
| --- | --- | --- |
| 安装 | 解析 → 并入数组 → 整份重写 | 落一个文件 |
| 卸载 | 从数组删 → 整份重写 | 删一个文件 |
| 更新 | 覆盖数组里的一项 | 覆盖一个文件 |
| 列出 | 读 59 KB 一次解析 | 读目录（几十个 stat）+ 缓存 |
| 导出/分享 | 从内部结构反序列化 | **直接拷贝文件**，格式保证一致 |
| 单份损坏 | 全丢 | 只丢那一份 |

### 5.3 slug 是身份，也是文件名

工作流新增一个稳定字段 `slug`：

```jsonc
{
  "app": { "name": "BOSS 直聘自动投递", "slug": "boss-auto-apply", "description": "...", "icon": "..." },
  "workflow": { "graph": { "nodes": [...], "edges": [...] } },
  "meta": { "slug": "boss-auto-apply", "source": "market", "installedAt": 1758765432109 }
}
```

- **文件名 = `<slug>.json`**，文件内 `meta.slug` 也存一份，读时校验一致（防手工改名）
- **去重键 = slug**，不是 `name`。同名不同 slug 是两个工作流，同 slug 才是同一个
- `name` 只做显示，改了不影响文件

**slug 校验**：`^[a-z0-9][a-z0-9-]{0,63}$`。不合格的一律拒绝，不做自动纠正（自动纠正会产生静默的重复）。

**slug 从哪来**：

| 来源 | 规则 |
| --- | --- |
| 市场安装 | 用市场 `index.json` 里的 `slug`，和文件内的 `meta.slug` 交叉校验，不一致就报错 |
| 本地录制 | `name` 是 ASCII 时转 kebab-case；否则用 `wf-<8 位哈希>`（哈希取 name + 创建时间），再查重 |

**冲突处理**：

| 情况 | 行为 |
| --- | --- |
| 同 slug、同 name | 覆盖（视为更新） |
| 同 slug、不同 name | **报错让用户选**：覆盖，或另存成 `<slug>-2`。不自动覆盖 |
| slug 非法 / 与文件名不一致 | 拒绝并提示 |

### 5.4 改动点

| 文件 | 改什么 |
| --- | --- |
| `RecordService.ts` | `workflowWrite` / `findWorkflow` / `deleteWorkflow` / `workflowUpdate` / `exportWorkflow` / `importWorkflowText` 全部改成文件读写 |
| `StorageService.ts` | 删掉 `workflows` 数组和 `saveWorkflows()`，换成一个 `workflows` 目录访问模块（带缓存 + 目录 mtime 失效） |
| `MarketService.ts` | `installMarketFile` 把市场条目的 `slug` 传进导入流程 |
| `ipc.ts` / `ipc/state.ts` | `storage.workflows` 的读取点改走新模块 |
| `tool-catalog.ts` | `workflow_list` / `workflow_write` 等同上 |
| `docs/环境与事件方案.md` §4.1 | 表格里 `workflows.json` 改成 `workflows\` 目录 |

### 5.5 迁移

1. 读 `workflows.json` 数组
2. 逐个算 slug（缺 `meta.slug` 时按 5.3 生成），写 `workflows\<slug>.json`
3. 全部写完并校验数量一致后，把原文件改名 `workflows.json.migrated`
4. **两个条目算出同一个 slug 时加 `-2`、`-3` 后缀并打一条警告**，绝不丢数据。

第 4 条和最初的"停下报错"不同：迁移发生在启动早期，为一条罕见重名让整个应用起不来不划算；数据安全靠"不丢"保证，而不是靠"不启动"。

## 6. 历史：SQLite，每环境一个

P1（目录迁移）之后，history 归到 `profiles\<env>\browserpilot\history.db`。这也和 Chrome 对齐：它的 profile 里就有一个 `History` 的 SQLite。

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;

CREATE TABLE history (
  id TEXT PRIMARY KEY,
  url TEXT NOT NULL,
  title TEXT NOT NULL,
  favicon TEXT,
  visited_at INTEGER NOT NULL
);
CREATE INDEX history_visited ON history (visited_at DESC);
CREATE INDEX history_url ON history (url);
```

- **写**：一次导航一条 `INSERT OR REPLACE`，不再重写 394 KB
- **读**：`history_list` 变成 `SELECT ... WHERE url LIKE ? ORDER BY visited_at DESC LIMIT ?`，走索引
- **上限**：保留 3000 条与环境一致，超了删最旧：
  `DELETE FROM history WHERE id NOT IN (SELECT id FROM history ORDER BY visited_at DESC LIMIT 3000)`
- **清空**：`env_delete` 直接删整个 `profiles\<env>`，不用再逐个 JSON 摘 envId

## 7. 运行记录：SQLite，全局一个

`schema` 草案（字段按现在的 `RunLog` 对齐）：

```sql
PRAGMA journal_mode = WAL;

CREATE TABLE runs (
  id TEXT PRIMARY KEY,
  workflow_slug TEXT NOT NULL,
  workflow_name TEXT NOT NULL,
  env_id TEXT,
  started_at INTEGER NOT NULL,
  finished_at INTEGER,
  status TEXT NOT NULL,        -- running | ok | error
  error TEXT,
  screenshot TEXT,
  outputs TEXT,                -- JSON 字符串
  files TEXT                   -- JSON 字符串
);
CREATE INDEX runs_started ON runs (started_at DESC);
CREATE INDEX runs_workflow ON runs (workflow_slug, started_at DESC);
```

- 保留策略变成一条 `DELETE FROM runs WHERE started_at < ?`，不再是"解析整个数组再过滤再写回"
- 运行记录页按时间倒序分页，走索引

## 8. 先做的：原子写 + 损坏隔离

不管迁不迁 SQLite，这两个函数都得改，而且必须在 P1 迁移之前——**迁移要把现有数据搬到新布局，如果目标存储会静默丢数据，迁移就是在雷区上走**。

```ts
function writeJson(name: string, value: unknown): void {
  const target = file(name)
  const tmp = `${target}.tmp`
  writeFileSync(tmp, JSON.stringify(value, null, 2), 'utf8')
  renameSync(tmp, target)                 // 同卷 rename 原子
}

function readJson<T>(name: string, fallback: T): T {
  const target = file(name)
  if (!existsSync(target)) return fallback
  try {
    return JSON.parse(readFileSync(target, 'utf8')) as T
  } catch (error) {
    const quarantine = `${target}.corrupt-${Date.now()}`
    try {
      renameSync(target, quarantine)
    } catch {
      // 挪不动就算了，至少不要让坏数据继续被当成好数据用
    }
    console.error(`[storage] ${name} 解析失败，已隔离到 ${quarantine}`, error)
    return fallback
  }
}
```

两个细节：

- `renameSync` 在同卷是原子的；跨卷会抛，所以 `.tmp` 必须和目标同目录
- 隔离而不是删除：坏文件可能是唯一的数据副本，留着至少能手抢救

## 9. 不做的

- **不把 `mcp.json` 换掉**：它是 SDK / Agent 的对外合同
- **不把 `settings` / `envs` 换掉**：小、启动早、可能被手改
- **不引入第三方 SQLite**（`better-sqlite3` 之类）：需要按 Electron ABI 重编，而 `package.json` 里 `npmRebuild: false` 正好会和它冲突；`node:sqlite` 已经够用
- **不做通用 ORM / 查询层**：三张表，手写 SQL 就够
- **不做跨环境的联合查询**：history 跟着环境走，要跨环境就是打开多个 DB，不合并

## 12. 删环境：Windows 上的目录占用

nv_delete 要删的是整个 `profiles\<env>`，但 Chromium 常常还攥着里面的文件。
实测两个坑，都已经处理：

1. **`session.clearStorageData()` 会把主进程 CPU 转满且不返回**。它在窗口刚关掉时调用尤其糟糕，
   曾让后续所有工具调用排队等死。现在不再调用——反正目录马上就删，清数据没有意义。
2. **`rm` 在 Windows 上会卡在文件锁上**。现在最多等 2 秒，删不掉就把环境 id 记进
   `orphans.json`，从环境列表里移除，**下次启动时在创建任何 session 之前再删一次**（那时没有句柄占用，能删掉）。

实测：
```
env_delete(从未打开过的环境)  => 1.4s 返回，环境消失，目录暂时留着，orphans.json 记一条
重启后                        => 目录已删，orphans.json 清空，profiles/ 只剩 env-default
```

还有一个现象值得记住：**删掉最后一个窗口会触发 `window-all-closed` → `app.quit()`**。
所以如果脚本把环境全删了，API 会"卡住"——其实是 App 正在退出，不是工具有问题。

## 13. 风险

| 风险 | 处理 |
| --- | --- |
| `node:sqlite` 在 Node 24 里仍标 experimental，API 可能变 | 已经实测在 Electron 45 可用；把 DB 访问集中在 `storage/db.ts` 一个文件，换实现只改一处 |
| 同步 API 阻塞主线程 | 只用于几十到几千行的小表，且都走索引；不在 DB 上做大范围扫描 |
| 两个工作流算出同一个 slug | 迁移时停下报错，不覆盖；安装时按 5.3 的冲突规则处理 |
| 工作流目录里文件很多 | 加内存缓存 + 目录 mtime 失效；100 个以内不考虑分片 |
| 迁移中途失败 | 每步都先写新位置再改旧文件；原文件改名而不是删除，留后悔药 |
